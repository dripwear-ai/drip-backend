## 3. Workstream A — Supabase identity-linking security

### Findings and scenario matrix

Supabase's identity-linking documentation describes email-based automatic linking, removal of unconfirmed identities to reduce pre-account takeover risk, and a distinct authenticated manual-link API (S01). General/local configuration distinguishes manual linking and email confirmation (S02/S03). These controls cannot be treated as an automatic-linking opt-out.

| --- | --- | --- | --- | --- |

| Unconfirmed password identity followed by matching Google identity | Documented unconfirmed-identity cleanup (S01) | Provider anti-preclaim protection is useful, but does not establish DRIP consent or complete existing-session invalidation | Require email confirmation; separately test old sessions and every account-creation order | **UNVERIFIED** for full policy |

The FAIL rows mean non-compliance with the owner's stricter policy, **not** a demonstrated Supabase vulnerability or arbitrary takeover by anyone who types an email. Email verification and trusted OAuth assertions mitigate threats, but the owner explicitly disallows automatic account access based on matching email. No penetration test, provider login or account claim was performed.

### Supported controls versus insufficient substitutes

S06's current upstream `master` source documents an experimental map separating linking domains and a deprecated predecessor. It is mutable development-source evidence, not a pinned release or proof of hosted availability. No managed configuration setting covering this feature was demonstrated in the reviewed public configuration references. The owner should obtain a supported configuration/release statement without sending credentials; support confirmation still needs isolated verification of OAuth callback, direct ID-token sign-in, email signup, email change, password addition, recovery, refresh and races.

Backend after-the-fact rejection can protect some DRIP operations, but it cannot undo provider-side identity linkage safely, and may deny the original user too. `providers` arrays, a client-provided provider name, generic `amr=oauth`, email matching, timestamps or an application pre-check do not establish an immutable external identity for each refreshed session. Post-login unlinking, undocumented database triggers and disabling only the manual-link button are not accepted mitigations.

**Recommended safe course:** keep combined authentication unavailable while seeking a supported pre-link control. If unavailable, present isolated provider-method projects as a separately reviewed Supabase-preserving design; budget for an additional admin realm and duplicate-account/recovery complexity. If that cannot satisfy the policy either, ask the owner to reopen provider/topology selection. Do not silently drop a login method, self-host experimental Auth, adopt another provider or weaken the no-link rule. Application authorization always maps immutable issuer/subject/realm to DRIP IDs, never email.

### Provider-independent enforcement remains mandatory

JWT verification requires exact approved issuer/audience/algorithm/realm, trusted JWKS origin, key-rotation and bounded outage handling; wrong-project keys, expired/malformed proof and API keys must be rejected (S08). PostgreSQL account/session/grant state remains authoritative after token validation. Supabase session time-box/inactivity controls have plan and refresh-time semantics; they do not alone supply immediate DRIP denial (S09). Keep the hard seven-day customer boundary, pending idle/custody/logout choices and prompt revocation; Redis loss cannot restore authority. Guest browsing must not create anonymous Auth users. Do not collect phones or add SMS; optional customer MFA remains C6. Admin AAL2 is assurance evidence, not an admin grant or automatically recent authentication (S10).

## 5. Workstream C — minimal R2 media architecture

**Recommendation, not deployed:** two buckets per environment initially: private intake/originals/rights evidence, and public approved derivatives. Private object categories have distinct application authorization/retention rules; do not expose the private bucket or assume a prefix alone is an access-control boundary. Separate rights-evidence storage can follow if required by access/retention separation. PostgreSQL owns source/rights/publication/object-version metadata, not the bucket listing. Future sellers can submit only to controlled intake after their backend scope is authorized; no seller public writes.

For the small admin pilot, prefer a **FastAPI-authorized streaming upload** with byte limits before buffering, bounded decoding and a server-chosen opaque key. This avoids initially depending on a browser PUT capability for hard pre-upload size enforcement. Streamed transport is not enough: limit concurrency, total bytes, pixel count and processing time; validate actual file signatures/decoding; sanitize EXIF/location metadata; generate only approved raster derivatives. Proposed formats JPEG/PNG/WebP; reject SVG/HTML and mismatched/polyglot/malformed content. Exact size/pixel caps need approval; the UI's 10 MiB local-preview limit is not a server policy.

Direct presigned PUT can be evaluated later for volume. R2 supports signed operations, but URLs are reusable bearer capabilities until expiry, not one-use approval. Bind method/key/expiry/content-type where supported, enforce final-size/content checks, disable arbitrary overwrite and expose no credentials. Private downloads can use short-lived authorized GET capabilities; do not log them. Presigned URLs operate on the S3 endpoint, not a public custom domain; signed POST-policy upload behaviour must not be assumed (S20). No arbitrary URL fetching/scraping is added.
