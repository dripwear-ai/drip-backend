# Batch 2A.1 — Authentication architecture resolution

Date checked: **2026-11-01**. Status: investigation and recommendation only; no implementation or provider configuration authorized by this document.

## 1. Executive summary

**Recommend Auth0 as the identity provider, retaining Supabase PostgreSQL and FastAPI.** Auth0 documents separate identities by default and linking only through an explicit flow. This is a better documented fit for DRIP's prohibition on automatic same-email association than the default Supabase or Clerk flows. Cognito is a technically viable alternative, particularly if Indian-region identity hosting and lower entry cost dominate, but returning to it requires explicit owner approval. No provider selection is changed by this report. The currently approved Supabase Auth direction remains recorded historically, with implementation blocked on this compatibility decision. [A1, A2, C1, K1]

Recommend **application-generated UUIDv7 using the repository's pinned Python 3.14 runtime, stored in PostgreSQL's native UUID type**. PostgreSQL 18 is necessary for the current native `uuidv7()` default, but is not inherently necessary to store application-generated UUIDv7. This requires an expressly approved transition from the existing default and migration assertion; changing only the Python generator would not make the repository portable. [U1–U5]

Supabase PostgreSQL **can remain approved independently of the authentication choice**. FastAPI can use PostgreSQL connectivity without making Supabase Auth the identity authority or exposing application tables through the Data API. Actual project version, region, roles, connectivity, backup policy and provisioning remain unverified. No claim is made that a project does or does not already exist. [S7–S10]

The architectural blockers are narrowed, not all closed. Owner decisions remain on provider/paid MFA entitlement, identity residency, C1–C7, D3 founder authority, and UUID migration strategy. The next gate is approval of these contracts plus authorization for isolated capability verification, not production implementation or rollout.

## 3. Supabase Auth findings

### 3.1 Managed behavior and policy result

Supabase documents automatic association of same-email identities and a separate manual linking facility. Disabling manual linking is not documented as disabling automatic association. Its protections around verified email and unconfirmed identities address provider security concerns but do not meet DRIP's additional requirement for explicit authorization to associate accounts. [S1, S2]

| Scenario | Documented behavior / classification | Security consequence for DRIP | Supported mitigation and result |
| --- | --- | --- | --- |
| Existing verified password identity, then Google identity with the same email | **VERIFIED:** default automatic linking behavior, subject to provider eligibility rules. [S1] | Another authentication method becomes associated without DRIP's explicit two-identity linking ceremony. A verified email is not that consent. | No demonstrated managed automatic-linking opt-out. **FAIL for the unchanged DRIP policy.** |
| Unconfirmed password signup followed by verified social login | **VERIFIED:** Supabase documents removal of unconfirmed identities when linking to mitigate pre-account-takeover. [S1] | Do not interpret an unconfirmed signup as durable proof of ownership, or infer that mitigation equals explicit linking permission. | Do not create authoritative DRIP ownership from unverified email. Default topology still fails the no-automatic-association rule. |

[S1] | An explicit path does not eliminate parallel automatic paths; beta is not a production assurance. | Require both identity proofs and consent in any approved linking design; enabling this alone does not resolve the default conflict. |
| Disable manual linking or hide Google on a screen | **VERIFIED/UNSUPPORTED:** manual setting is documented; suppressing UI is not provider enforcement. [S1, S2] | Direct provider calls can bypass UI choices. | Not an acceptable remedy. |
| Before-user-created hook rejects collisions | **VERIFIED:** hook applies before creation of a new user. [S4] | Not demonstrated to intercept all identity attachment to an existing user. | **UNVERIFIED** as a complete linking firewall; do not rely on it. |

| Use upstream provider-linking-domain controls | **EXPERIMENTAL:** upstream configuration has experimental provider-linking-domain settings. [S3] | Build-level capability is not evidence of managed availability, production support or complete password/recovery isolation. | Do not recommend it for launch. No live collision or takeover test occurred. A takeover is not asserted for every same-email flow. The confirmed issue is a policy mismatch; recovery, email reassignment and unverified claims introduce additional scenarios that require hostile-path testing.

The reverse signup order matters: Supabase's FAQ describes an obfuscated response, without a verification email, when email signup follows an existing same-email OAuth account. It also documents adding a password to an OAuth account. Those paths require explicit recovery/credential-attachment analysis; separate signup UI is insufficient. [S1] Upstream `ExperimentalConfiguration.ProviderLinkingDomains` uses `GOTRUE_EXPERIMENTAL_PROVIDER_LINKING_DOMAINS`; `ProvidersWithOwnLinkingDomain` is deprecated in favor of it. These are inspected source identifiers, **not proposed DRIP environment variables**. Operator-controlled/self-hosted configuration is distinct from a managed-project production feature. [S3]

### 3.2 Option B: redesigned Supabase topology

An explicit registration screen in one project does **not** fix automatic linking. Nor does attaching a DRIP account only after login if the provider subject has already been shared across identities.

A possible isolation design is separate managed Auth projects/realms for Google-only and password-only accounts, with FastAPI mapping `(issuer, subject)` independently and initially disabling cross-realm links. This would need **provider-enforced**, not UI-only, prevention of password creation/recovery in the Google realm, prevention of social login in the password realm, isolated callbacks/keys, separate administrator assurance, and proof that every recovery/update path preserves separation. The reviewed evidence does not demonstrate that complete managed configuration. **Option B is UNVERIFIED, not an approved workaround.**

Even if isolation is proved, it brings extra projects, issuers, mail/recovery configuration, incident handling and potential same-email duplicate accounts. Any later user-requested cross-realm association must prove control of both identities and decide ownership/data conflicts. It must not silently combine wishlists. Self-hosting the experimental Auth control moves deployment, patching and availability responsibility to DRIP and still needs security verification; it is not the minimal production-ready recommendation.

### 4.1 Auth0 identity architecture and required enforcement

**VERIFIED provider capabilities:** Google OAuth social connections and email/password database connections are documented independently of the linking examples. Recommend Auth0's managed credential store, not a custom password database inside DRIP; choose email identifiers without enabling phone collection. Google production client ownership and callback configuration remain C2 decisions. [A9, A10]

**CONDITIONALLY VERIFIED DRIP design:** separate identities are a starting point, not a provider guarantee of the whole policy. Review tenant Actions, extensions, rules, connection settings and management access to exclude same-email auto-linking. Do not issue identity-linking management permissions to ordinary customer/admin application sessions or build a linking endpoint in the initial scope. Restrict and audit provider-control-plane operators and management credentials too: a privileged provider linking API is not itself proof that both people authenticated. A later approved linking service must verify recent control of both identities, explicit intent and replay protection before invoking it. Test direct calls, not only hidden buttons. [A1, A2]

FastAPI should accept only access tokens intended for the registered DRIP API. Verify the signature using trusted issuer discovery/JWKS, an explicitly allowed signing algorithm, exact configured issuer, required audience, expiry and other required claims; never select a key URL from untrusted token input. Unknown keys require bounded refresh and fail closed if they cannot be verified. Existing PyJWT is a possible implementation library, not evidence that validation is implemented. Client binding, assurance and session identifiers must be specified for the selected token profile; do not assume every access token contains `auth_time`, `amr` or `sid`. An ID token or a Google API token is not a substitute. [A3, A11]

Customer and admin login must remain separate trust boundaries. The remote admin path must prove approved MFA and recent authentication, plus current DRIP-side grants. Token scopes, provider roles, email verification or membership in a tenant alone cannot confer founder authority. Provider recovery must not override suspension. Refresh rotation and provider logout/recovery complement, but cannot replace, PostgreSQL-backed DRIP session expiry, revocation and authorization. The exact factors, enrollment/recovery, token custody, idle duration and provider configuration remain pending. [A4–A6; C1/C4 decisions]

### 7.2 Approach comparison

| Dimension | Approach 1: database-native UUIDv7 | Approach 2: application UUIDv7 + UUID storage |
| --- | --- | --- |
| Current repository fit | Current model default, migration assertion and tests match. | Requires approved changes to default ownership, writer contracts and tests. |
| Platform coupling | Requires verified PostgreSQL 18/native function on all intended targets. | Compatible with PostgreSQL UUID storage independently of native generator; runtime must supply a correct v7 generator. |
| SQL/ORM behavior | Omitted ID can be generated consistently by DB default. | Every authorized writer supplies ID; ORM default does not cover raw SQL. Missing-ID raw SQL must fail rather than fall back to UUIDv4. |
| Clock/order | Database clock; still not a substitute for business ordering. | Backend clocks; monitor skew, retain PK uniqueness and do not promise total order. |
| Operational simplicity | Simplest while all targets are demonstrably 18. | Simplest portable choice on pinned Python 3.14; one generation owner avoids dual-default ambiguity. |
| Recommendation | Retain current behavior until a transition is approved; viable if managed 18 is confirmed. | **Recommended future strategy**, subject to migration/acceptance gate. No current schema/default changed. |

### 7.3 Safe transition and legacy identifiers

1. Before an authorized implementation, inventory actual revisions, tables, writers, IDs and foreign keys in an explicitly approved disposable/staging target. No such inventory was performed against a database here. Preserve existing UUID values, including v4, and all foreign-key relationships. Never regenerate primary keys merely to obtain v7 ordering.
2. For existing PostgreSQL 18 databases on the current lineage, a future forward migration can change defaults after the new write contract is ready. Coordinate deployment so every new writer supplies UUIDv7; preserve rollback compatibility and test direct SQL plus ORM behavior. Do not edit applied 0001/0002 to conceal their original behavior.
3. For a fresh pre-18 target, a later revision alone cannot fix the earlier assertion. Prepare a **separately reviewed portable bootstrap/baseline and legacy-upgrade transition design**, preserving the original migration files and recording which lineage actually ran. Alembic supports multiple bases/environments, but that does not prove a safe DRIP graph. The design must demonstrate how future revisions apply consistently to both histories without accidentally replaying 0002. Do not blindly stamp an unexecuted revision or use a merge that reintroduces the failing ancestor. [U6]
4. If managed 18 is confirmed and selected, the alternative is to keep the current lineage and make only forward changes. This is a deployment choice, not a claim that UUIDv7 inherently requires 18. If the portable baseline cannot be proved safe, pause that migration batch; do not reset user data to force it through.
5. Test new v7 version/variant, uniqueness, serialization, application and raw-SQL insertion, legacy-ID reads, FK integrity, upgrade/rollback and failure of missing/invalid IDs. Do not enforce v7 retrospectively on historical or provider identifiers. No performance or ordering guarantee should be claimed without measurement.

The current test asserting exclusively server-generated UUIDs represents the old contract. Replacing it after an approved design change must add equally strong application-generation and missing-ID regressions; it must not be silently weakened to make a new target pass. Rollback preserves data and identifiers; PostgreSQL downgrade or database reset is not a rollback plan.

### 7.4 Explicit forward-only transition proposal

**VERIFIED source finding:** there are only two current migration files. `0001` creates `pgcrypto`; `0002` runs a `DO` capability assertion and has a no-op downgrade. It creates no table, persistent constraint or UUID function. There is no later migration operation requiring PostgreSQL 18. The model mixin and temporary test probes do depend on native generation, but no concrete application entity/table is defined in the inspected source. Actual database contents remain **UNVERIFIED**.

Consequently, there is no persistent "PostgreSQL 18 assertion" for a future migration to drop. Changing a model default is also not DDL against already-created tables. If an existing database truly contains only this foundation, switching future entity creation to application UUIDs needs no `ALTER TABLE` solely for an absent default. If inventory discovers actual owned tables/defaults, a forward migration must change those specifically. A new revision that does nothing but promise to remove the earlier assertion is not a fix.

**Proposed minimal convergence sequence, requiring owner approval and isolated proof:**

1. Freeze the reviewed historical migration files and inventory the authorized target's revision, DRIP-owned schema, defaults, extensions and writers. Stop on unknown tables/revisions or non-disposable scope. Do not inspect or modify Supabase-managed `auth`/`storage` objects as if DRIP owned them.
2. Define one immutable portable schema checkpoint, called **T** here only as a design label. A future successor revision can mark that checkpoint and remove verified owned native defaults where needed. With the current empty entity schema it may be a documented compatibility checkpoint rather than a DDL change. Introduce a backend-owned `uuid.uuid7()` callable for every new DRIP entity path; do not accept client-selected primary keys as authoritative. Approved imports/repair tools must use the same generation contract. Keep legacy and external identifiers unchanged.
3. Existing PostgreSQL 18 installations follow their normal forward upgrade to T. Deploy ID-supplying writers before removing an existing default; remove that default once every writer is compatible. New tables have no native generator dependency. A temporary native-default coexistence window on PG18 is an explicit rollout step, not the final dual-source design.
4. For a **fresh, explicitly authorized pre-18 target**, do not execute the historical chain and expect a successor to rescue it. Use a separately reviewed bootstrap that creates the exact DRIP-owned schema at T, verifies all required extension/privilege/default/constraint effects, then records T only after equivalence succeeds. Alembic documents schema creation followed by revision stamping. [U9] This is an explicit baseline adoption, **not a claim that 0002 ran**. Audit the bootstrap route and intentionally unexecuted historical capability check. Do not stamp 0002 as a workaround, blindly stamp `head`, or infer schema completeness from `create_all()` alone. The snapshot must cover non-table effects too. No old file is pruned or rewritten.
5. Compare the owned schema reached by a fresh PG18 historical upgrade, an existing PG18 upgrade, and a portable pre-18 bootstrap. All converge at T and then execute the same subsequent migrations. If safe verified baseline adoption is not approved, keep pre-18 initialization blocked or separately review a new lineage; do not invent a bypass in runtime configuration.
6. Restrict pre-18 rollback to compatible checkpoints; it must not restore a nonexistent native `uuidv7()` default. Keep legacy history available for PG18 rollback/forensics without claiming every historical target is portable. Never downgrade the database engine, recreate data, or rekey rows. Older binaries requiring native generation cannot be a pre-18 rollback target.

This replaces the preliminary need for an unspecified dual-lineage design with a smaller **candidate** based on a documented Alembic baseline mechanism. It is **CONDITIONALLY VERIFIED**, not a tested DRIP migration plan. A single ordinary forward migration **cannot** remove the clean-install PG18 dependency while replaying 0002 unchanged. A forward upgrade plus explicitly approved, verified portable bootstrap **can potentially remove it for future operation and fresh targets**, without rewriting history. Managed project compatibility is still a gate.

Acceptance: prove schema equivalence at T, preserved existing IDs/FKs, no default calling an unavailable function, per-insert UUID version 7 and RFC variant, exact string round-trip, concurrent uniqueness, all authorized write paths, raw SQL missing-ID rejection, rejection of inappropriate client IDs, legacy-v4 reads, interrupted bootstrap refusing to stamp, unknown/nonempty schema rejection, upgrade/retry and compatible rollback. Keep historical native PG18 tests as historical coverage; add portable-generation tests instead of describing them as the same contract. PostgreSQL UUID storage alone does not enforce v7 on arbitrary SQL input; write privileges and application validation must enforce the approved new-ID contract.

## 8. Recommended provider-independent architecture

Proposed boundary: customer/admin clients authenticate with an approved IdP; FastAPI verifies the appropriate access credential and resolves a stable internal account; PostgreSQL holds DRIP account status, sessions, grants, ownership and application data. Supabase Auth need not be used to access Supabase PostgreSQL. A service-role key is not a SQL connection credential and is not needed merely to run FastAPI SQL queries. [S8]

Keep the abstraction small: one verifier for the selected provider producing a normalized trusted principal (allowlisted issuer, immutable subject, intended client/API binding, relevant assurance/time claims), one identity-binding service, and DRIP authorization services. Do not build a general identity broker or support several live providers just to demonstrate portability. Mapping is conceptually unique on `(issuer, subject)`; email is mutable contact data, never an ownership key. Any future link/migration is an explicit reviewed operation with evidence and audit, not an email-based UPSERT.

Application foreign keys, wishlist ownership, grants and sessions reference the **DRIP internal user UUID**, not an Auth0 `user_id`/subject or email. The external binding references that internal ID. A future provider migration changes verified bindings while retaining the internal ID and application ownership; it does not derive a new user key from the provider string. Recovery that changes the external subject needs an approved recovery/rebinding procedure with proof and audit, never same-email discovery. Credential hashes, MFA enrollment, provider sessions and recovery factors are not assumed portable. Revoked/deleted mappings must not resurrect accounts through a subsequent same-email login.

Maintain separate customer and administrator authentication boundaries. A separately configured admin tenant/realm with restricted enrollment and approved MFA is the recommended starting topology, **not yet an approved configuration**. Separate applications alone must not be assumed to provide adequate isolation; prove token/realm/client distinctions, factor enforcement and current DRIP grants. Enroll two individually designated founders through the controlled local bootstrap policy; no public bootstrap endpoint or self-editable role.

Keep seven-day maximum customer authorization lifetime and immediate DRIP-side revocation authoritative in PostgreSQL. C4 must specify the session identifier/binding that connects provider tokens to a DRIP session, rotation races, logout, idle expiry and treatment of an otherwise valid token after revocation. Do not assume all providers emit the same `sid` claim or that signature verification proves current grant status. Redis may assist rate limits/cache/coordination but must not become the only revocation or ownership record.

Use least-privilege application SQL roles and a distinct migration role; never ship database or provider management credentials to clients. Prefer application tables outside exposed Data API schemas; separately verify grants/RLS and deny anonymous/authenticated Data API access where no client use is approved. PostgreSQL RLS behavior depends on role privileges; owner/service-role bypass is not an authorization strategy. External JWTs do not automatically make `auth.uid()` or Supabase Auth-owned foreign keys appropriate for DRIP. Connection pooling/session context and TLS must be reviewed before any RLS-based context scheme. [S8, S11]

FastAPI owns business logic and authoritative financial arithmetic. Money remains integer minor units/Decimal; MoneyINR wire amounts are digit strings, with general zero permitted and catalogue prices still strictly positive under existing rules. LLMs receive only authorized tool-mediated data; no direct database access. Public guests receive only eligible public DTOs. Cloudflare media/DNS, Firebase mobile support, Redis ephemerality, source/rights gates and P2-B restrictions are unchanged by this identity proposal. Secrets remain out of source, URLs in logs, reports and notifications.
