## 1. Settled direction — do not reopen

Auth0 is the selected external authentication provider; Supabase PostgreSQL is the intended primary database; FastAPI owns business logic/authorization. Permanent DRIP internal IDs are application-generated UUIDv7. Exact external binding uses `(issuer, subject)`, never email or provider IDs as internal PKs. Automatic linking is prohibited. PostgreSQL is authoritative, Redis ephemeral, money exact, LLM database access prohibited, schema changes Alembic-managed, and historical migrations immutable. Google/password, no phone/SMS, guest public browsing, authenticated permanent wishlist and existing founder/MFA/governance policies remain preserved. No database/user/session/grant integration is inferred from approved JWT primitives.

The current source still has a native UUID server-default mixin and a historical PG18 assertion. Those facts coexist with the approved future application-generation direction until the owner approves its transition. Do not resolve the conflict by rewriting history. Older provider-selection/status text in ADRs/reports is historical; these two planning documents record current precedence without editing it.

## 3. What can and cannot proceed after review

**Current task:** documentation only. No implementation is eligible merely because these documents are complete.

**Smallest recommended first authorized slice:** after D03/D04 approval, 2B-2a may introduce exact SQLAlchemy metadata and pure storage-contract tests, with no connection, endpoint, provisioning, activation or historical migration edit. D01/D02 must settle before committing to executable migration/repository/security mechanics. This separates narrow preparation from claims that production identity is ready.

**Full database foundation acceptance:** needs D01–D04 plus D08's disposable proof of PG17/PG18 convergence, real unique/FK/concurrency/role behavior, all regression checks, owner review and explicit acceptance. If managed checks remain unrun, label that stage blocked rather than declare Supabase integration verified. D05–D07/D10 must close before the corresponding managed/runtime release; D09 before later exposed account behavior. A blanket claim that every C1–C7 detail must be solved to write a passive column is unnecessary, but unresolved security decisions cannot be bypassed to activate an account.

**Deferred unrelated decisions:** catalogue cohort/source/image rights, retailer domains, price freshness, R2 delivery, Firebase scope, seller execution, native distribution and OOTD ownership remain their separate milestones. They do not block two private identity tables. No wishlist/session/grant/catalogue schema is introduced to anticipate them. Batch 2B-3 and P2-B remain separately authorized work.
