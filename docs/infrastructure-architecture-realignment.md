# Infrastructure architecture realignment

**Decision checkpoint: 2026-10-31, Asia/Calcutta. Status: provider direction approved by the owner; detailed design proposed for review; implementation NOT authorized by this task.**

## 1. Executive decision and precedence

The owner has selected **Supabase Auth instead of Amazon Cognito**, **Supabase PostgreSQL as the authoritative database**, **Cloudflare for DNS/CDN/security and object-storage evaluation (particularly R2)**, and **Firebase for mobile support services including FCM and Crashlytics**. FastAPI retains business logic and API ownership. Redis remains ephemeral. R2 evaluation is approved; a specific bucket, delivery architecture, paid plan or production storage rollout is not yet approved. Optional analytics is not enabled by this decision.

This dated record supersedes only conflicting provider-selection assumptions in [ADR 0002](adr/0002-cognito-authentication-decision.md), [Phase 2](phase-2-specification-and-plan.md) and [P2-0](p2-0-contracts-and-acceptance.md). Their historical approvals remain intact. In particular, Phase 2 §19 and the [frontend closeout](frontend-first-implementation-verification.md) recorded that Supabase was only an alternative **at that time**; today's owner decision changes that direction. This file does not retrospectively change what Gate B tested or reopen accepted Next.js/Expo maintenance. The [readiness audit](p2-a-readiness-audit.md) remains historical evidence of dependency gates, not a current provider recommendation.

**Two hard compatibility gates precede authentication/database implementation:**

1. Supabase documents automatic linking of identities with the same email. That conflicts with the preserved no-automatic-linking policy. Disabling manual linking does not establish that automatic linking is disabled. A supported, testable prevention mechanism or an explicit owner-reviewed policy/design amendment is required; no post-login unlinking workaround is approved.
2. DRIP's existing migration requires PostgreSQL 18 and native `pg_catalog.uuidv7()`. The selected Supabase project's version/capability has not been inspected. Managed PostgreSQL availability must be proved before migrations are attempted; no downgrade of the requirement is inferred from provider selection.

Everything below labelled **proposal** is a design recommendation, not an approval or implementation claim. Existing provider-independent requirements remain mandatory. No real project identifiers, accounts, credentials, domains, deployment targets or catalogue records are invented.

## 3. Preserved requirements and proposed responsibility boundaries

The following remain approved, tracing to Phase 2 §§3/6/8/9 and ADR 0002 §§2, 12–17:

- Google and email/password customer sign-in; no customer phone collection or routine SMS OTP. Customer MFA is not compulsory; optional MFA remains C6. Guest public browsing needs no provider account, anonymous-auth user or account-specific guest session.
- Permanent PostgreSQL-backed wishlist and online cross-device synchronization; guest save preserves the card, requests sign-in, requires explicit confirmation and only reports success after the API commits the save. Authentication alone is not synchronization.
- Separate customer/admin authentication; individual founder accounts, equivalent ordinary permissions, no shared credentials or self-approved grants. Ordinary access changes require the other founder's approval. Local initial grants require a controlled development-only bootstrap, never a public endpoint or editable role flag.
- Admin MFA is waived only on a development-machine-restricted instance with development data and no tunnel/shared exposure. Shared/remote test and production require MFA and current DRIP grants. A cloud hostname or an `ENVIRONMENT=development` string does not qualify a remotely exposed instance for the exception.
- Emergency suspension may be invoked immediately by either founder against the other with their own identity, reason/confirmation and recent environment-appropriate authentication. Confirm authoritative grant/session denial before success; record attribution; notification failure cannot undo confirmed suspension. Review, remediation and the other founder's approval precede explicit restoration. Never automatically remove customer access/data or restore privileges after a timeout/provider recovery.
- Seven-day hard maximum customer session lifetime plus a separately chosen idle timeout; immediate DRIP-side denial/revocation; verified-channel recovery; private-data deletion target within 30 days; minimal approved audit retention. C1/C4/C7 details remain open.
- Exact money and existing catalogue rules remain: general `MoneyINR` output permits zero through signed BIGINT maximum as paise digit strings; catalogue prices require strictly positive paise. No float arithmetic. Nullable inventory is unknown, not stock. D2/D5 business limits/freshness are not settled here.
- Real rights-cleared catalogue and approved retailer redirects only; no fabricated content, scraping, orders, payments, settlement or new AI access to databases. Guest OOTD access remains approved **when** its separately gated implementation exists; P2-B authorization is not granted here.

**Proposed topology:** mobile/web -> provider login for identity proof; mobile/web -> FastAPI for public catalogue and all DRIP account/privileged operations; FastAPI -> Supabase PostgreSQL for authoritative business state. Firebase handles mobile delivery/diagnostics, Cloudflare handles approved edge/media duties, Redis handles bounded ephemeral work. No client writes directly to business tables, no Firebase Auth/Firestore business store, and no Supabase Edge Function business layer replacing FastAPI.

Cloudflare DNS/CDN does not select FastAPI hosting, a Redis host, a web host, a job runner or a deployment platform. Those remain operational decisions. No architecture diagram arrow grants credentials or authorizes provisioning.

## 4. Supabase Auth proposal and security gates

### 4.1 Environment and realm separation

**Proposal:** separate development, shared/test and production provider environments. Evaluate separate customer and admin Supabase Auth projects per environment to preserve distinct issuers and enforceable admin policy. The customer/business project would contain the authoritative DRIP business schema; an admin identity project would contain only its provider-managed auth state, not a second wishlist/catalogue source of truth. This costs more operational effort; a single project's two screens or publishable keys do not by themselves create separate authentication realms. An alternative topology requires explicit proof that customer credentials cannot cross into the admin realm and owner approval under C1/C2/C5.

Google configuration requires owner-controlled consent/project ownership, minimal reviewed scopes/attribute mapping, distinct approved web/native/test clients, exact callback and post-login/logout allowlists, and account-collision testing. Recommend browser authorization-code + PKCE for the initial native/web flow, subject to compatibility review; do not assume Cognito Managed Login has an identical Supabase-hosted UI replacement. Supabase's OAuth callback and DRIP's application return URL are different redirect legs. No wildcard production redirects, client secret in mobile bundles, arbitrary return-to URL, or acceptance of a raw Google token as a DRIP API credential. Sources: [Supabase Google](https://supabase.com/docs/guides/auth/social-sign-in/auth-google), [PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow).

Keep phone and anonymous sign-ins disabled in the proposed configuration. Email/password requires verified-email gating for private access and recovery through an approved verified channel. Passwords are handled by the provider, not retained by DRIP. Owner-reviewed password/reset/email-change rules, enumeration-resistant responses, redirect validation, recovery throttles and email delivery must precede real-user acceptance. Supabase's bundled SMTP is intended for restricted non-production use; a verified production sender/custom SMTP and delivery monitoring remain C5/C6, without requiring SES specifically. Sources: [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [rate limits](https://supabase.com/docs/guides/auth/rate-limits).

### 4.2 Identity linking: unresolved blocking incompatibility

[Supabase identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking) explicitly describes automatic same-email linking, separately from opt-in manual linking. The approved DRIP policy is no automatic identity merging/linking and linking disabled initially. **The reviewed documentation does not establish a managed configuration switch that satisfies that policy for both Google and email/password in one realm.**

Before enabling both methods, obtain authoritative vendor confirmation of a supported pre-link control and demonstrate it across OAuth/code/token entry paths, or return to the owner with a separately reviewed alternative topology/policy. Splitting methods into isolated identity realms is an option to evaluate, not a selected fix; it adds issuer, recovery and duplicate-account complexity. An application lookup after the provider has already linked identities, disabling only `linkIdentity()`, or relying on verified email is insufficient proof. No speculative hook is claimed to solve this.

**Proposed mapping:** DRIP-generated account ID distinct from provider ID; unique `(issuer, subject, realm)` binding to one DRIP principal, with provider identity metadata only as necessary for reviewed collision handling. Provider subject values are opaque identifiers; do not require Supabase-generated IDs to be DRIP UUIDv7. Email is mutable contact data, never the authority to merge, grant admin or inherit a wishlist. C3 must specify normalization, verified-channel changes, duplicate/collision UX and recovery without revealing another account. No identity schema or new DTO is created by this report.

### 4.3 JWT verification and request authorization

**Proposal:** prefer project-supported asymmetric signing keys; use the existing backend cryptographic tooling if compatible, rather than automatically adding an SDK. Pin each trusted issuer, expected audience, algorithm set, realm and HTTPS JWKS location in reviewed configuration. Supabase publishes project JWKS at `/auth/v1/.well-known/jwks.json`; its claims are not Cognito's `token_use`/app-client contract. Sources: [Supabase JWT verification](https://supabase.com/docs/guides/auth/jwts), [API key distinctions](https://supabase.com/docs/guides/getting-started/api-keys).

Future verifier acceptance must reject wrong issuer/audience, unsupported algorithm, `none`, algorithm/key confusion, unknown key after a bounded refresh, malformed/oversized tokens, expired/not-yet-valid proof, missing required subject/session claims, wrong environment/realm and API keys masquerading as user tokens. Validate clock skew and issued-at rules under C4. Never derive a JWKS fetch URL from attacker-supplied `jku`/issuer; prevent unbounded refresh amplification. Cache public keys with bounded rotation/outage behavior; unknown/untrusted keys fail closed. Never use the generic `SECRET_KEY` or legacy `HS256` setting as a Supabase JWT verification shortcut.

After cryptographic verification, FastAPI resolves the immutable binding and checks authoritative DRIP account, session and (for admin) grant/assurance state. A provider `authenticated` role, editable `user_metadata`, email domain or frontend role display is not an admin grant. Every private lookup enforces ownership. Public endpoints expose eligible published DTOs only, without account/wishlist/admin fields. Invalid credentials on a protected request must not silently downgrade it to guest access.

### 4.4 Session, revocation and recovery contract

Supabase issues short-lived access tokens and rotating refresh tokens; reuse handling and session limits have provider-specific semantics, and configured timeouts are not equivalent to immediate request-time DRIP denial. Some controls depend on the selected plan. Review exact plan support rather than adopting defaults. Source: [Supabase sessions](https://supabase.com/docs/guides/auth/sessions).

**Proposed initial boundary:** bind verified provider sessions to durable PostgreSQL DRIP sessions. Enforce a non-sliding 168-hour customer deadline and reviewed idle limit on every private request, including immediately after refresh; refreshing or reopening the app must not restart the original deadline. Whether fresh provider reauthentication creates a new DRIP session, the admin maximum, and reliable evidence of recent authentication remain C4/C1. Reject inactive/revoked/missing DRIP sessions even with a valid provider JWT. Redis eviction/outage must not restore authority.

Pending C4 choices include direct provider JWT plus durable binding versus opaque DRIP session, web token custody and CSRF protection, native SecureStore custody/backup behavior, refresh serialization/race handling, access-token lifetime, logout one/all-device semantics and notification of provider-side disablement. **Proposal:** a server-mediated web refresh boundary with Secure/HttpOnly cookies and CSRF controls; native secure storage for protected refresh credentials. These are different custody designs, not a claim that a browser Supabase client can read HttpOnly refresh cookies. Any server-held refresh secrets require encryption/key lifecycle review; do not expose provider tokens through business DTOs, URLs, logs or analytics.

DRIP-origin disablement commits denial first; provider revocation is a separately tracked operation and cannot roll back protection on provider failure. C4 must also define how out-of-band provider-console disable/logout is detected and enforced, and the failure policy if that check is unavailable. A local signature check alone cannot prove current provider account status. Define in-flight privileged-write serialization/rechecks so an authorization decision made before suspension cannot silently commit an unauthorized change afterward; exact concurrency contract remains pending.

### 4.5 Admin assurance and deletion

Supabase exposes MFA assurance levels, including `aal2`; that is useful evidence but does not alone prove recent authentication. Evaluate non-phone factors against C1, including recovery and availability on the chosen project/plan. Do not approve TOTP or a freshness interval merely by choosing Supabase. No remembered-device or password-recovery bypass of required admin assurance. Source: [Supabase MFA](https://supabase.com/docs/guides/auth/auth-mfa).

Preserve ADR 0002 §§13–17 local bootstrap, mutual approval and emergency procedure. The future emergency UI/API must distinguish confirmed suspension from pending/failed notifications. Notification provider/channel/retries and auditable fallback remain C1/D3; FCM selection does not automatically make push an adequate founder security-alert channel.

Account deletion requires immediate DRIP denial, removal of private wishlist/profile/session/device-token data within the approved 30-day target, coordinated provider account deletion and retry/escalation evidence. Preserve only approved minimal audit/suppression records, never secrets. C7 must cover Supabase backups, Auth data, media, Firebase identifiers/crash records and any notification provider, including restoration suppression and backup expiry. Do not promise immediate deletion from immutable backups or complete provider deletion without evidence; reconcile this with the owner's lifecycle requirements before rollout.

## 5. Supabase PostgreSQL, RLS and migrations

### 5.1 PostgreSQL 18 compatibility gate

The [Supabase upgrade guide](https://supabase.com/docs/guides/platform/upgrading) reviewed here discusses managed version/extension upgrade constraints, including PostgreSQL 17; it does **not** establish that the owner's unselected project runs PostgreSQL 18. PostgreSQL documents native [UUIDv7 functions](https://www.postgresql.org/docs/18/functions-uuid.html). Availability on the actual selected Supabase environment is **NOT VERIFIED**.

Before use, owner-authorized isolated staging evidence must establish server version >=18, native UUIDv7/version extraction, pgcrypto permission required by 0001, actual ORM/direct-SQL server defaults and both existing migrations' behavior. If unavailable, stop: either obtain a compatible Supabase offering or request an explicit architectural review of an alternative UUID/version strategy and migration history. Do not remove 0002, silently stamp it applied, rewrite 0001, or substitute client UUIDv4.

### 5.2 Connection and least-privilege design

**Proposal:** keep SQLAlchemy/asyncpg and `DATABASE_URL` for FastAPI. Use TLS with certificate/hostname validation, a dedicated runtime DB role, conservative pool/concurrency budgets and separate migration/admin credentials. Prefer direct or session-pooled connectivity appropriate to hosting/network availability; use a separate approved migration connection. Supabase's shared transaction pooler has prepared-statement limitations. Selecting it requires explicit SQLAlchemy/asyncpg prepared-statement and transaction-state tests, not simply changing a URL or assuming an asyncpg setting configures SQLAlchemy's separate cache. Source: [connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres).

No production credential or complete connection URL belongs in logs, reports, client variables or Git. Preserve percent-encoded credential regression coverage. Existing development/test URLs remain local; do not turn a missing managed configuration into fallback to a personal/local database. Environment configuration must reject mismatched project/issuer/DB realms and development secrets in deployed environments. Network/credential rotation and backup restore require separately authorized operations.

### 5.3 FastAPI-only business access and RLS

**Proposal:** an explicitly private DRIP business schema, excluded from exposed API schemas, with Data API access disabled where compatible and no business-schema grants/default privileges for `anon`/`authenticated`. Realtime business-table access is not introduced. Supabase documents that grants/default exposure and RLS both matter; inspect them rather than assuming new tables are private. Sources: [securing the Data API](https://supabase.com/docs/guides/api/securing-your-api), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

For future DRIP private tables, propose RLS as defense in depth alongside service ownership checks. Runtime DB roles must be non-owner, non-superuser and lack BYPASSRLS; evaluate FORCE RLS where ownership could otherwise bypass policies. Any transaction-local principal/realm context is supplied only by authenticated FastAPI services, never trusted from request headers or client SQL, with missing context denying private access and pool-reuse isolation tests. This context limits mistakes, not a fully compromised API server. Public catalog reads use an explicitly restricted published/eligible projection; guest requests never acquire admin DB authority.

Supabase publishable keys are client configuration, not secrets or authorization. Supabase secret keys/legacy `service_role` credentials bypass RLS and must remain server-only, scoped to necessary provider administration, not routine business queries. Prefer a constrained SQL runtime role over a broad service-role client. Disabling Data API access is not equivalent to disabling Auth; prove selected settings preserve login while blocking business table access. Sources: [API keys](https://supabase.com/docs/guides/getting-started/api-keys), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

### 5.4 Schema ownership, transition and local testing

Alembic remains the sole DRIP schema history. Supabase owns its managed `auth`/storage/system schemas; never autogenerate migrations against or downgrade those schemas. Future reviewed migrations may create a private schema/roles/policies, account/identity/session/grant/audit structures and later media/device registrations. These are conceptual requirements, not approved table definitions or permission to add all models now. If existing DRIP tables/data exist elsewhere, inventory and plan an explicit non-destructive relocation/backfill; no automatic schema move or cascade-delete dependency on provider tables.

Use a controlled SQL principal for limited provider session-status reads if selected under C4, or a supported provider API; approve that integration separately. Do not create a fragile cross-project SQL foreign key to admin Auth. Logical `(issuer, subject)` references require explicit deletion/reconciliation handling. Keep provider-owned UUIDs separate from DRIP-generated keys.

Keep existing local PostgreSQL 18/Redis disposable tests unchanged. Future Supabase-specific tests need a **separate**, explicitly allowlisted local/emulated or disposable cloud environment and target guard, not broader values for the current guard. Offline JWT/session doubles are suitable for unit tests but cannot verify provider linking, MFA or delivery. A local Supabase stack is an option after authorization and version/port/volume review, not an instruction to run the CLI now. Local/cloud version mismatch must be visible, not hidden by passing ordinary PostgreSQL tests.

Before a real data cutover: inventory sources; back up and rehearse restoration in isolation; verify row counts/constraints/roles/defaults; arrange a bounded write freeze and single-writer switch; retain old data securely until reviewed. Define RPO/RTO, backup/PITR plan and deletion implications under C5/C7. Rollback is a reviewed application/connection cutback with reconciliation, not blind destructive downgrade, dual writers or provider-account deletion. No such operation occurred here.

## 6. Cloudflare proposal

### 6.1 DNS, edge security and caching

Propose owner-controlled zones and separately reviewed API/web/media subdomains per environment, validated origin TLS, restricted origin ingress and WAF/rate-limit rules suited to the purchased plan. DNS alone does not protect an origin that can be bypassed. Preserve certificate validation, exact CORS origins and OAuth return allowlists; trust forwarded client-IP headers only from configured proxies. Source for origin TLS behavior: [Cloudflare Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/).

Authenticated APIs, callbacks, sessions, admin, wishlist and errors with private state must be `no-store` and bypass shared caching; never key private responses only by URL. Public catalog caching needs eligibility/withdrawal invalidation and owner-reviewed TTLs. Avoid caching transient authorization errors as public content. Logs must redact credentials, cookies, authorization headers, recovery codes and signed URLs. WAF does not replace FastAPI authorization or Supabase's direct-endpoint abuse controls. C6 must specify degraded rate-limit behavior; Redis failure must not turn sensitive actions into unlimited attempts. Any durable retry/audit requirement lives in PostgreSQL, not Redis alone.

### 6.2 R2 evaluation and secure upload lifecycle

**Proposal for a later authorized media batch:** separate private quarantine, public-approved derivatives and private rights/evidence storage, isolated between development/shared/production environments. Exact buckets, regions/jurisdictions, retention, lifecycle rules, file limits and costs remain open. A location hint must not be advertised as a contractual residency guarantee. R2 is an S3-compatible API, not an instruction to retain AWS Cognito/SES or provision AWS resources. Evaluate against the simpler existing approved image-host approach before adding processing work.

Proposed sequence: authenticated current admin with publication rights requests a short-lived upload capability -> FastAPI allocates an opaque server-chosen object key in quarantine and records ownership/state -> upload -> trusted verification checks actual content, byte/pixel limits, decoder/decompression safety, supported raster format, EXIF/metadata removal and rights evidence -> approved safe derivative becomes publishable through the catalogue service. Uploaded bytes and client-supplied MIME/filename are not proof of safety or rights. Reject active SVG/HTML by default in this proposal; approve exact formats/limits separately. UI's existing 10 MiB local preview is not an approved backend limit.

Direct R2 presigned PUT is an option, not a completed upload API. Bind method/key/expiry/content-type where supported, restrict CORS, never permit caller-selected overwrite/list/read credentials, and treat the URL as a secret bearer capability. Enforce upload limits at a capable trusted boundary and on stored content; a presigned URL/MIME header is not a guaranteed size or content validator. If required pre-upload limits cannot be enforced, evaluate a streaming gateway with hard limits before approval. Orphan cleanup/quota/retries must be bounded and idempotent, preserving rights records under C7. R2 presigned URLs use its S3 API endpoint, not a public custom domain. Source: [R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/).

No seller direct publishing, customer uploads, unauthenticated capability issuance, arbitrary URL downloader or automatic merchant scraping is implied. The current admin source-URL workflow remains the baseline until the owner authorizes media upload/processing and rights transfer; infrastructure selection does not make previously deferred processing part of P2-A automatically.

### 6.3 Delivery, withdrawal and environments

Evaluate a custom media domain with immutable versioned derivative keys; keep quarantine and approval documents private. R2 public buckets/custom domains support delivery features but differ from authenticated S3 access. Do not use an unrestricted development `r2.dev` endpoint as production access control. Source: [R2 public buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/).

Publication must bind a validated derivative to approved product/source/rights state in PostgreSQL. Withdrawal removes eligibility immediately at the API; media origin access and CDN purge/TTL must meet a separately accepted rights-withdrawal SLA. Immutable URLs and caching can leave copies reachable; purging one cache cannot recall downloaded copies. If stricter revocation is required, evaluate an authorization-aware delivery gateway rather than promising instant recall of public objects. No private approval evidence should ever enter the public bucket/cache.

Development uses no production bucket credentials/data; offline storage doubles can test policy, while signed-upload/CORS/purge acceptance requires an owner-authorized isolated environment. Edge/media outages must produce truthful unavailable states and never substitute fabricated products or bypass rights checks.

## 7. Firebase and Expo proposal

### 7.1 Messaging

Firebase is selected for support services, **not** authentication or business persistence. Evaluate one push integration: (a) Expo native device tokens with direct FCM on Android and APNs on iOS, or (b) React Native Firebase Messaging with FCM on both platforms, backed by APNs on Apple devices. The latter adds native configuration; the former must not mislabel an APNs token as an FCM token. An Expo push relay would add another processor and is not selected here. Sources: [Expo direct push](https://docs.expo.dev/push-notifications/sending-notifications-custom/), [Firebase Apple setup](https://firebase.google.com/docs/cloud-messaging/ios/get-started).

Future authorized implementation needs owner-controlled Firebase projects, environment-specific app registration, Android signing/app identity, APNs credentials/entitlements and physical-device access under D7. Propose least-privilege server messaging credentials and HTTP v1/provider-supported sending; no service-account private keys in apps or Git. Store necessary authenticated device registrations/consent/ownership in PostgreSQL, protect tokens as sensitive identifiers, rotate/unbind on logout/account deletion and prevent account-A pushes after device switches to B. Do not create a guest account/tracking identity just to browse; guest marketing subscriptions are not approved.

Notification permission must be contextual and denial must not block discovery. Payloads must omit sensitive personal/admin data and never be authoritative for price, stock, wishlist or security state. On opening, authorize and refetch via FastAPI. Validate deep links; handle foreground/background/terminated states, invalid tokens and duplicate delivery. Provider acceptance is not evidence the device received/read a message. Security-event notification delivery/retries/fallback remain a separate C1/C7 decision.

### 7.2 Crashlytics and optional analytics

Expo documents that native React Native Firebase requires native code/development builds and does not run in Expo Go. The Firebase JS SDK is not a substitute for native Crashlytics.
